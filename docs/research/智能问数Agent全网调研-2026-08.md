## 第一梯队 · 语义层 / Ontology 驱动的对话 Agent(最对标 Data-Agent)

这一组的共同特征:**把"业务语义/知识建模"做成 Agent 可消费的一等公民**,而不是把 schema 直接丢给 LLM。这与你的 ontology 设计意图完全一致。

### 1.1 WrenAI(Canner)— MDL Context Layer + 开源 GenBI 引擎 🟢

- **GitHub**:<https://github.com/Canner/WrenAI> · **License**:Apache 2.0 · **Docs**:<https://docs.getwren.ai>
- **定位**:开源 GenBI(generative BI)引擎——让 AI agent 在一个可信任的 **context layer** 上 *生成 → 部署 → 治理* BI 产出。
- **2026-05-07 重大重构**(训练知识里没有):Wren Engine 已合并进本 repo 的 `core/`,旧 `Canner/wren-engine` 归档;旧的 Docker chat-first BI 产品移到 `legacy/v1` 分支(标签 `v1-final`),改名 **Wren GenBI Classic**;主线转向 **agent-driven**(CLI + skills,驱动 Claude Code / Cursor / Cline / Codex)。

**核心架构(代码级)**

```
core/
  wren-core/         Rust 语义引擎(基于 Apache DataFusion)
  wren-core-base/    共享 manifest 类型 + MDL builder
  wren-core-py/      Python 绑定(PyPI: wren-core)
  wren-core-wasm/    WebAssembly 构建(npm: wren-core-wasm)——浏览器端跑语义引擎
  wren/              Python SDK + CLI(PyPI: wrenai)
  wren-mdl/          MDL JSON Schema
sdk/
  wren-langchain/    参考 Agent SDK 集成(LangChain / LangGraph)
skills/              Agent skills(上下文撰写)
```

**关键抽象:MDL(Modeling Definition Language)** —— 这就是它的"本体":
- `models / columns / relationships / views / cubes / metrics`
- **RLAC / CLAC**(行级 / 列级访问控制)是 MDL 的一等字段,不是事后补丁

**三拍子设计**:
1. **Generate**:agent 把业务问题转成 *governed* SQL + charts。链路 = **schema-aware retrieval → MDL planning → dry-plan validation → 结构化错误(with hints)**,核心是"宁可结构化失败,不要 confidently wrong"。
2. **Deploy**:用 `wren-core-wasm` 把任意答案变成浏览器端 dashboard,一条命令(`wren genbi deploy`)部署到你的 Vercel / Cloudflare Pages。
3. **Know**:让一切可校验的知识活在版本化文件里——`instructions.md`(业务定义)、`queries.yml`(已批准样例查询)、LanceDB 本地记忆索引(**hybrid retrieval**,召回历史相似查询)。

**治理与正确性原语**(路线图已部分落地):functions、dry-plan、row limits、access control;规划中 = audit logs、rate limits、approval workflow、data-flow inspector、value profiling、rich retrieval、golden eval runner。

**分发**:CLI(`pip install wrenai`)+ `npx skills add Canner/WrenAI`(给 AI 客户端装一个 ~50 行 discovery stub),agent 按 `wren skills get <name>` 拉工作流指南、`wren ask "<q>" --guided|--direct` 包装问题。

**对 Data-Agent 的直接启示**:
- MDL ≈ 你的 `ontology/v1/*.json`;但 WrenAI 把 **context layer(instructions.md 业务定义 + queries.yml 样例)做成 agent 一等输入**——这正是你的 `business_rules.json`(运行时零读取)该成为的东西。
- **dry-plan validation + structured errors with hints** = 你的 `queryPlanner` 缺的"宁可失败也不幻觉"层。
- **golden eval runner** = 你评测只覆盖路由、答案/SQL 行/引用从不校验的缺口。
- `wren-core-wasm` 浏览器端跑语义引擎,是个低成本的"语义层沙箱"思路。

### 1.2 Cube(cube-js)— Headless 语义层标杆 🟢

- **GitHub**:<https://github.com/cube-js/cube> · **License**:Client MIT / Backend Apache 2.0 · **Docs**:<https://docs.cube.dev>
- **定位**:开源 **headless 语义层**(不自带 UI)——定义 metrics/dimensions/joins/access rules 一次,通过 **SQL / REST / GraphQL** API 暴露给下游任意消费者(BI 工具、自定义应用、**AI agent**)。
- **商业模式**:Cube(商业)= Cube Core + Analytics Chat(agentic)+ workbooks/dashboards + embedded + managed + RBAC + 多租户 + Tableau/Power BI/Excel/Sheets 集成。数据模型双向兼容(Core ↔ Cube)。

**核心架构原理**

- **data model 即代码**:用 JS/TS 写 `cube()` 定义,声明 measures / dimensions / joins / granularity;一处定义、多处消费——这是"语义层即治理"的工业实践。
- **relational caching engine**(预聚合):对 API 请求提供亚秒级延迟 + 高并发。这是 WrenAI 没有的能力。
- **多源**:Snowflake / Databricks / BigQuery / Presto / Athena / Postgres 等所有 SQL 源。
- **AI agent 消费**:agent 不直接碰表,而是通过 Cube 的 SQL/REST/GraphQL API 查"已治理的 metric"——**agent 永远拿不到错误口径**,因为口径在语义层锁死。

**对 Data-Agent 的直接启示**:
- Cube 的 **"定义一次,SQL/REST/GraphQL 三接口暴露"** 正是你 `queryCompiler` 的目标终态——你的语义查询目前只编译成内部 SQL,没暴露成标准 API 给多消费者。
- **relational caching**(预聚合)对你"测试覆盖度/DDP/KPI"这类重复高频度量是性能刚需,你目前每次现算。
- Cube 把 **access rules 写进 data model**(RLAC),与你的 `sensitivity` 字段 + scope policy 同构,但 Cube 是生产级落地的。

### 1.3 dbt Semantic Layer / MetricFlow 🟢[已抓取]

- **GitHub**:<https://github.com/dbt-labs/metricflow>(原 Transform 开源,2023 被 dbt Labs 收购)· **Docs**:<https://docs.getdbt.com/docs/build/build-metrics-intro> · **License**:Apache 2.0(0.209.0+;此前曾为 AGPL → BSL)
- **定位**:把 metric 做成语义层一等公民,解决"同一个 DAU 在 Tableau/Looker/自建看板里数字不一致"的问题。**"MetricFlow"之名 = metric 请求被编译成 *dataflow-based query plan*,再优化、翻译成引擎专用 SQL**(README 原文验证)。

**核心抽象(semantic model spec)**
- `entities`:join key(primary/unique/foreign),用于 measure/dimension 之间的连接
- `measures`:可聚合的数值(加和/去重计数/百分比/中位数…)
- `dimensions`:切片维度(时间/类别/字符串)
- `metric types`:simple / derived(公式组合)/ cumulative(累计窗口)/ ratio(比率)
- 处理 **multi-hop joins**(事实表 ↔ 维度源多跳连接)

**关键能力**:MetricFlow 引擎把 metric 请求自动转成最优 SQL(选 join 路径、避免 fan-out),口径一致;dbt SL 把它暴露成查询 API 供下游消费。

**🆕 Open Semantic Interchange(OSI)倡议(2025 新动向,训练知识未覆盖)**:MetricFlow 现由 dbt Labs 维护并纳入 **Snowflake 主导的 OSI 开放语义交换标准**——联合头部厂商建立"语义信息定义与交换的开放标准",实现 **AI/BI 跨平台互操作**。对你的 Data-Agent 是重要信号:**语义层正在标准化**,`ontology/v1/*.json` 长期应考虑对齐 OSI 这类开放规范,避免成为孤岛。

**对 Data-Agent 的直接启示**:
- 你的 `ontology/v1/metrics.json`(30 度量含 DDP/regression_coverage/function_coverage)**字段结构与 MetricFlow 的 measures+metric types 高度对应**——你已经有了 MetricFlow 的"数据形态",但缺它**自动 join 路径选择 + fan-out 防护 + metric query API** 的引擎。
- MetricFlow 是"metric 即契约"的工业标准,值得对照它的 schema 规范补全你的度量定义(尤其是 derived/ratio/cumulative 类型)。

### 1.4 Palantir Foundry Ontology 🔴(商业标杆,原理对标)

- **官网**:<https://www.palantir.com/platforms/foundry/ontology> · 文档:<https://www.palantir.com/docs/foundry/ontology/>
- **定位**:**本体 = 企业所有数据 + 逻辑 + 动作的统一可执行语义层**。这是"ontology 级企业数据"的极端形态,也是你最远期的对标。

**核心组成**
- **Object Types**:业务实体(及其 properties / primary key),数据沉淀为"对象集"(Object Set)
- **Link Types**:实体间关系(图)
- **Action Types**:**改数据/触发流程的函数**,带参数校验、权限、审计——agent 调 action 就是在受控地改企业状态
- **Functions**:本体上的查询/计算逻辑(可被 action / AI 调用)
- **OSDK**:把 ontology 生成强类型 SDK(TypeScript/Python/Java…),开发者用类型安全的对象编程
- **AIP(Artificial Intelligence Platform)**:LLM agent 通过 ontology action 读写企业——**AI 的每个动作都绑在本体的 action 上,带权限与审计**

**对 Data-Agent 的直接启示**(这是最重要的一面镜子):
- Palantir 把本体做成 **"可执行的企业操作系统"**——关系 / 规则 / 动作 **运行时全部生效**。
- **对照你的现状**:你的 `relationships`(`getRelationship` 零调用)、`business_rules`(运行时零读取)、5 条 `constraints`(仅 2 条生效)、3 个 `actions`(Octane 回写,声明但未必接 action 层)——**目前是"声明摆设",Palantir 是"声明即执行"**。
- 你的 `ontology/v1/actions.json` 若要达到 Palantir 哲学,应当每个 action 是带参数校验+权限+审计的可执行函数(agent 调用即触发,而非仅生成 SQL)。

## 第二梯队 · 开源企业数据 / NL2SQL Agent

这一组不强调"语义层建模",而是把 **Agent 编排 + 生产化(RLS/沙箱/可观测/多源)** 做到工业级——正好对照你 Data-Agent 的 Agent 编排 5 缺口。

### 2.1 DB-GPT(eosphoros-ai)— AWEL 编排 + Skills + 沙箱 🟢

- **GitHub**:<https://github.com/eosphoros-ai/db-gpt> · **License**:MIT · **论文**:[2312.17449](https://arxiv.org/abs/2312.17449)、VLDB demo [2404.10209](https://arxiv.org/abs/2404.10209)、ROMAS [2412.13520](https://arxiv.org/abs/2412.13520)
- **定位**:开源 **agentic AI data assistant**——连接数据库/CSV/数仓/知识库,自主写 SQL 与 Python,跑可复用 skills,产出图表/仪表盘/HTML 报告,**所有执行在沙箱**。

**核心架构(代码级)**
- **AWEL(Agentic Workflow Expression Language)**:核心编排抽象,用 DAG 表达 agent 工作流(类 Airflow-for-agents)。这是 DB-GPT 区别于"一次 prompt 出 SQL"的关键——工作流可编排、可复用、可托管。
- **Skills**:把领域知识 / 分析方法 / 执行流程打包成可复用技能(甚至能从 GitHub 导入 skill),正是企业沉淀分析资产的载体。
- **沙箱执行**:Python / code / 工具在隔离环境跑(`sandboxed execution`),安全 + 可复现。
- **Text2SQL 微调**:DB-GPT-Hub,支持 LLaMA/Qwen/Baichuan/InternLM/ChatGLM 等全家桶微调。
- **多源**:关系库 + CSV/Excel + 文档 + 知识库(RAG,默认 ChromaDB)+ 混合源工作流。
- **多模型**:DeepSeek/Qwen/GLM/Llama/Gemma/Yi/Mixtral…(SMMF 统一管理)。
- **ROMAS**:role-based 多 agent 系统(给 DBA 监控/规划用)。
- 部署:PyPI `dbgpt-app`,`uv run dbgpt start webserver`,UI 在 :5670;或 Docker / 源码。

**对 Data-Agent 的直接启示**:
- **AWEL** 对照你的 LangGraph 6 节点——DB-GPT 把工作流做成"可声明、可托管、可复用"的资产,你的工作流目前硬编码在 `langGraphChatRuntime.mjs`。
- **沙箱执行**是你"agent 写代码/跑 Python 分析"的安全前提;你目前 Python sidecar 是直接 spawn,无沙箱。
- **Skills** 概念 ≈ 你的 `actions` + 业务工作流,但 DB-GPT 做成了可导入/分享的包。
- **可观测**:DB-GPT 有 `debugging` / advanced tutorial 体系,你 `失败 run 不留 audit` 的缺口在这里反差明显。

### 2.2 Vanna(vanna-ai)— 2.0 重写:user-aware + RLS + 流式 🟢

- **GitHub**:<https://github.com/vanna-ai/vanna> · **License**:MIT · **Docs**:<https://vanna.ai/docs>
- **定位**:Vanna 2.0 是**完全重写**,从 0.x 的 `VannaBase` 类方法式 → **Agent-based + 用户感知 + 生产就绪**。

**核心架构(代码级)**
- **UserResolver / User / RequestContext**:你定义如何从请求(cookies/JWT/OAuth)抽取用户身份 → 注入 `User(id, email, group_memberships)`。
- **User-Aware Tools**:所有 tool 继承 `Tool[T]` 基类,声明 `access_groups`;执行时 `context.user` 自动注入,**SQL 自动按用户权限做行级过滤(RLS)**。
- **ToolRegistry**:注册 `RunSqlTool` / 自定义 tool;tool 返回 `ToolResult(success, result_for_llm)`。
- **LlmService**:`AnthropicLlmService(model="claude-sonnet-4-5")` 等,LLM 可插拔。
- **流式 SSE**:`POST /api/vanna/v2/chat_sse`,后端流式推送结构化 UI 组件(progress → SQL → table → chart → summary),前端用预置 `<vanna-chat>` web component 渲染。
- **生产化扩展**:Lifecycle hooks(quota / logging / content filtering)、LLM middlewares(caching / prompt eng / cost tracking)、Conversation Storage(按用户持久化)、Observability(tracing + metrics)、Context Enrichers(RAG / memory / docs)。
- 架构是 FastAPI + Agent + ToolRegistry;任何 LLM / 任何 DB / 你自己的 auth。

**对 Data-Agent 的直接启示**:
- **UserResolver + User-Aware Tools + RLS** 是企业落地的硬需求——你的 `scopePolicy.mjs`(`actor.scope.mandatory`)已有 scope 概念,但 Vanna 把它下沉到**每个 tool 自动按 user group 过滤 SQL**,比你手工 scope 更彻底。
- **Lifecycle hooks / LLM middlewares** 正是你缺的"传输可观测 + retry/backoff + 模型降级"(你的 5 缺口之一:`companyChat.mjs` 裸 fetch)。
- **流式结构化 UI 组件**比你的 SSE 文本流更适合 BI 场景(table/chart 分块流)。

## 第三梯队 · 学术 SOTA(BIRD / Spider 榜单方法)

这批不强调企业可运行性,而是把 **schema linking、候选生成、自校验、多 agent 分工** 推到极致。对你的 `resolver` 消歧 / `queryCompiler` 校验有直接技术借鉴。

> **基准科普**:BIRD-SQL(<https://bird-bench.github.io/>)= 真实跨库大库 benchmark;Spider / Spider 2.0(<https://yale-lily.github.io/spider>)= 经典 + 企业级真实数仓。榜单见 <https://www.paperswithcode.com/sota/text-to-sql-on-bird>。

### 3.1 CHESS — 4-agent 流水线(BIRD SOTA 开源代表)🟢

- **GitHub**:<https://github.com/ShayanTalaei/CHESS> · **论文**:[arXiv 2405.16755](https://arxiv.org/abs/2405.16755)
- **4 个专精 agent**,各打一个痛点:
  1. **Information Retriever(IR)**:用 **minhash + LSH + 向量库** 提取相关 catalog 与"最相似的数据库 value"(解决大库值匹配)。
  2. **Schema Selector(SS)**:**剪枝大 schema** 成子 schema(报告:accuracy +~2%、token 降 5×)。
  3. **Candidate Generator(CG)**:生成高质量候选 SQL 并**迭代 refine**。
  4. **Unit Tester(UT)**:用 **LLM 自然语言单元测试** 校验查询语义正确性。
- **战绩**:BIRD test **71.10%** accuracy,距最强专有方法 ~2%,LLM 调用减少 **83%**;开源模型里 SOTA(隐私友好)。
- **代码结构**:`run/run_preprocess.sh`(建 minhash/LSH/向量索引)+ `run/run_main_ir_cg_ut.sh` / `run_main_ir_ss_ch.sh`(两种配置);LLM 在 `run/langchain_utils.py` 的 `get_llm_chain()` 可换。

**对 Data-Agent 的直接启示**:
- **IR 的 minhash+LSH+向量 value 匹配** 正是你 `resolver` 的子串首匹配消歧该升级的方向(你 `semanticCandidate.mjs` 想做但没接线的 LLM 候选,这里是一套完整方案)。
- **SS 的 schema 剪枝** 对你"28 实体/50 维度"的中等规模现在收益不大,但实体增长后必备。
- **UT 的"LLM 自然语言单元测试"** 是你评测缺的"答案级校验"的廉价实现思路。

### 3.2 MAC-SQL — 3-agent 协作(Selector / Decomposer / Refiner)🟢

- **GitHub**:<https://github.com/wbbeyourself/MAC-SQL> · **论文**:[arXiv 2312.11242](https://arxiv.org/abs/2312.11242)(COLING 2025)
- **3 agent**:`core/agents.py` 定义三类,`core/chat_manager.py` 管通信,`core/const.py` 存 prompt 模板:
  1. **Selector**:从全 schema 选相关表/列(等价 CHESS 的 SS,但更早提出)。
  2. **Decomposer**:把复杂问题**分解成子问题**(CoT),生成 SQL。
  3. **Refiner**:执行报错 → 据错误信息**自动修订 SQL**(self-correction)。
- **SQL-Llama**:开源微调(CodeLlama-7b,v0.5,3375 训练实例,HuggingFace `IceKingBing`)。
- 评估在 BIRD(EX/VES)+ Spider 上做,`evaluation/` 下有脚本。

**对 Data-Agent 的直接启示**:
- **Refiner(self-correction on execution error)** 正是你工具循环里"空结果自愈(自动注入 `diagnose_analytics_empty`)"的学术版——MAC-SQL 把它做成了 *执行报错→修订 SQL→再执行* 的闭环,你可以参考其 prompt 设计。
- **Decomposer 的 CoT 分解** 对你"测试覆盖率回归""缺陷多维下钻"等多步问题有用。

### 4.1 Snowflake Cortex Analyst 🔴

- **文档**:<https://docs.snowflake.com/user-guide/snowflake-cortex/cortex-analyst>
- **核心**:**语义层 YAML(`_semantic_models.yaml`)** —— 用声明式 yaml 描述表/列/指标/同义词/verified SQL,作为 LLM 的"已验证上下文"。LLM 只在语义层约束内生成 SQL,显著降低幻觉。
- **理念**:**"语义层 yaml = 治理 + 抗幻觉"**。和你 `ontology/v1/*.json` 同构,但 Snowflake 把它做成 Snowflake 原生 + Cortex LLM 一体的商业产品。
- **对标启示**:你已走在相同路线上(JSON-Schema 本体驱动 LLM)。Snowflake 的差异是**云原生集成 + 企业分发**;你的差异可以是**垂直领域(汽车测试)的语义深度**。

### 4.2 ThoughtSpot Sage 🔴

- **官网**:<https://www.thoughtspot.com/product/ai>
- **核心**:**Search-driven BI + Sage(LLM)**。用户用搜索框打自然语言 → LLM 转 Answer/Search;强调 *conversational analytics* + *Liveboards*。
- **理念**:**把"问数"做成搜索体验**,而非 chat。LLM 不止生成 SQL,还做意图理解 + 自动可视化推荐。
- **对标启示**:ThoughtSpot 的"搜索框 + 自动可视化"是 BI 用户体验标杆;你的 SSE chat 形态可以补一个"搜索式"快捷入口。

### 4.3 Hex Magic 🔴

- **官网**:<https://hex.tech/magic/>
- **核心**:Hex 数据科学 notebook/项目平台 + **Magic(LLM agent)**。Magic 在 notebook 上下文里做数据清洗/探索/建模/洞察,**语义层 + 自动洞察**。
- **理念**:**agent 不止写 SQL,还做完整数据科学工作流**(Python + SQL + 可视化 + 叙事)。
- **对标启示**:Hex 把 agent 嵌入"数据科学家工作流"而非"业务问答";若你的用户是测试工程师(偏分析),Hex 的 notebook-embedded agent 形态比纯 chat 更贴需求。

## 六、Data-Agent 专项诊断:优点 / 短板 / 推荐

### 6.1 你的相对优势(对照全网,哪里领先)

1. **语义层建模质量已进第一梯队**。`JSON-Schema 2020-12 + 跨工件校验器(validator.mjs)+ 内容哈希指纹(registry.mjs)+ 敏感度脱敏`——这套**程序化治理**比 CHESS/MAC-SQL/DB-GPT/Vanna(都**没有本体**)强一个代差;与 Cube / dbt-SL / WrenAI / Palantir 同属"声明式语义层"阵营,且你的 schema 校验+指纹比 WrenAI 更严格(它靠 MDL + git review)。
2. **垂直领域 ontology 深度 = 不可替代资产**。28 实体/27 关系/12 业务规则/30 度量(DDP/regression_coverage/function_coverage)/78 zh-CN vocab——这是 WrenAI/Cube/dbt-SL 这类**通用语义层根本没有**的领域知识,对应 Palantir"行业本体"的护城河哲学。MindsDB 的转型警告恰好说明:**通用 NL2SQL 会被吞掉,垂直 ontology 不会**。
3. **中文原生**。zh-CN vocab + 中文 NL→SQL,比 CHESS/MAC-SQL/DIN-SQL(纯英文 BIRD/Spider)更贴你的用户;XiYanSQL 是少数同样做中文的,可对标。
4. **Agent 编排骨架正确**。LangGraph 6 节点 + per-call 策略门控 + 空结果自愈(`diagnose_analytics_empty`)——与 Vanna(单 agent)、DB-GPT(AWEL)同代,骨架没问题。

### 6.2 你的关键短板(对照全网,哪里落后,附可借鉴项目)

### 6.3 分优先级推荐(P0 / P1 / P2)

> 排序逻辑:P0 = 补生产化硬伤(不解决会出事故/无法迭代);P1 = 让你设计却没生效的"本体智能"真正生效(对应你《目标架构设计.md》的 P1 项);P2 = 跃迁与差异化。

**P0 — 立刻补生产化硬伤**
- **P0.1 失败 run 留 audit + tracing**(借鉴 Vanna / Dataherald):`persistRuntimeState` 改为无论成败都写;加 token/错误分类。这是当前最大风险盲区。
- **P0.2 传输 retry/backoff/模型降级**(借鉴 Vanna middlewares / MindsDB Model Router):给 `companyChat.mjs` 加 timeout/retry/熔断/模型 fallback。
- **P0.3 评测扩到答案/SQL/引用**(借鉴 CHESS exec acc / WrenAI golden eval):你的 golden 应从"断言路由"升级到"断言 SQL 行结果 + 引用命中工具结果 + LLM-as-judge 答案质量";顺带修 `agent-golden` 断言 ≥10 但文件仅 9 条的 bug。

**P1 — 让本体智能真正生效(你已有的设计,缺接线)**
- **P1.1 `business_rules.json` 接 `queryPlanner`**(借鉴 WrenAI `instructions.md`/`queries.yml` + Palantir Action):把 KPI 公式 / Q-Gate / owner 语义解析成可执行校验函数,在 planner 调用。这是你目标文档 P1.5 的核心。
- **P1.2 `semanticCandidate.mjs` 接 resolver**(借鉴 CHESS IR):让 LLM 候选消歧真正喂给 `resolver.mjs:236/257/278` 的 candidate 分支(目前死代码);中文场景叠加 XiYanSQL 的 schema linking 经验。
- **P1.3 relationships 运行时图遍历**(借鉴 WrenAI MDL / Palantir Link Types):让 27 条关系支持多 hop 查询,替换 Python 硬编码 traceability + 消除 `ontology_context.py:164` 双目录漂移。
- **P1.4 SQL Refiner 闭环**(借鉴 MAC-SQL Refiner):执行报错 → 自动修订 → 再执行,与你的空结果自愈合成完整 self-correction。

**P2 — 跃迁 / 差异化**
- **P2.1 多 agent 拆分**(借鉴 CHESS / MAC-SQL):把单链路拆成 linking→生成→校验→修订 分工,可参考 CHESS 的 IR/SS/CG/UT。
- **P2.2 沙箱执行**(借鉴 DB-GPT):agent 写代码/跑 Python 前先沙箱。
- **P2.3 per-user RLS**(借鉴 Vanna):scopePolicy 下沉到每 tool 自动过滤。
- **P2.4 语义层 API 化**(借鉴 Cube / MetricFlow):把 `queryCompiler` 产物暴露成 SQL/REST/GraphQL 标准接口,让多消费者(BI/嵌入/app)复用同一口径。

### 6.4 战略提示(对抗 MindsDB 式吞并)

MindsDB 从 NL2SQL 转型为通用 AI workspace 是个信号:**纯"中文 NL→SQL"单点产品长期会被通用 agent + 数据连接器替代**。你的护城河应锚定在**垂直(汽车测试缺陷)的 ontology 深度 + 治理 + 中文**,而不是和通用 agent 拼 SQL 准确率——后者是 CHESS/MAC-SQL 的赛道,你拼不过也不该拼。**Palantir 的"本体即企业操作系统"是终局参照**:声明的关系/规则/动作都该运行时生效,你目前三块都是摆设,这是最大也是最有价值的差距。
