# WrenAI 混合集成落地方案
## 把 wren-core 引擎嵌入 Data-Agent,同时保留 JSON 本体为唯一源

- **日期**:2026-08-03
- **适用项目**:`Data-Agent`(Node.js 主代理 `server/` + Python sidecar `backend/analytics/` + JSON-Schema 本体 `ontology/v1/`)
- **决策依据**:用户选定 **混合路线(嵌入引擎 + 架构借鉴)** + **保留 JSON 本体、只借设计**
- **配套文档**:`智能问数Agent全网调研-2026-08.md`(为什么选 WrenAI)、`智能问数Agent目标架构设计.md`(你的 P1 目标)

---

## 0. 核心判断(先读)

| 问题 | 结论 | 证据 |
|---|---|---|
| wren-core 能否库式嵌入(非 CLI)? | ✅ 能 | `from wren_core import SessionContext`;`pip install wren-core-py`(PyO3+Maturin) |
| 能否接受**运行时构造**的 MDL(不落地文件)? | ✅ 能 | `SessionContext(base64_mdl_json)` 直接吃 base64 MDL JSON 字符串 |
| 能否复用你现有 Python sidecar? | ✅ 能 | 加到 `backend/analytics/` FastAPI(:3003),不新建运行时 |
| 保留 JSON 本体为唯一源可行吗? | ✅ 可行 | JSON→MDL 在 sidecar 内**运行时派生**,MDL 不持久化、不维护双本体 |
| 部署风险? | ⚠️ Linux ARM64 无预编译 wheel | 需 Rust 工具链自编(见 §7) |

> **一句话**:不"抄袭"代码,而是**把 wren-core(Rust 语义引擎)当 sidecar 库嵌入你的 backend/,输入用你的 JSON 本体运行时生成 MDL,输出 planned/dry-run SQL**;Node 侧借鉴它的 context layer / eval / strict governance 设计。你的自有架构、JSON 治理、agent 编排全部保留。

## 2. 模块 A · JSON→MDL 编译器(`ontology2mdl.py`)

目标:把你的 `ontology/v1/*.json` 机械映射成 WrenAI MDL manifest(dict)。**这是整个方案的枢纽**——它决定了你能从 wren-core 拿到多少红利。

### 2.1 字段映射表

| 你的 JSON 本体 | → | WrenAI MDL | 说明 |
|---|---|---|---|
| `entities[].id` | → | `models[].name` | 实体即模型 |
| `entities[].source.table` / `readModel` | → | `models[].table_reference{catalog,schema,table}` | 物理表定位 |
| `entities[].primaryKey` | → | `models[].primary_key` | |
| `entities[].properties[]{id,type}` | → | `models[].columns[]{name,type}` | type 需映射(见 2.2) |
| `dimensions[]`(含 entityId) | → | 对应 model 的 dimension column | 切片维度 |
| `metrics[]`(含 KPI:DDP/regression_coverage) | → | 对应 model 的 measure column | 聚合度量;derived/ratio 用 MDL expression |
| `relationships[]`(predicate + sourceFields + allowedJoinPaths) | → | `relationships[]`(this→target + join fields + type) | 27 条关系 → MDL join 规格 |
| `sensitivity`(实体/属性级) | → | MDL access control / 或映射到 strict governance | 见 §5 |
| `constraints` / `business_rules` | → | (不进 MDL)在 sidecar 用 strict_mode + 自研校验消费 | 见 §4/§5 |

> ⚠️ MDL 的 `relationships` / measure expression 的**精确字段名以 `core/wren-mdl` 的 JSON Schema 为准**(本次 README 抓取 404,落地前需抓 `wren-mdl/schema/*.json` 或 `docs/core/guides/modeling/` 核对)。上表是结构级映射,字段名可能微调。

### 2.2 类型映射(Python 骨架)

```python
# backend/analytics/ontology2mdl.py
import base64, orjson
from pathlib import Path

TYPE_MAP = {
    "string": "varchar", "text": "varchar", "keyword": "varchar",
    "integer": "integer", "long": "bigint", "double": "double",
    "float": "double", "boolean": "boolean", "date": "date",
    "datetime": "timestamp", "timestamp": "timestamp",
}

def build_manifest(compiled: dict) -> dict:
    """把 ontology.compiled.json → WrenAI MDL manifest(dict)。"""
    models = []
    for ent in compiled["entities"]:
        cols = []
        # 维度列
        for d in compiled["dimensions"]:
            if d.get("entityId") == ent["id"]:
                cols.append({"name": d["id"], "type": TYPE_MAP.get(d.get("type","string"),"varchar")})
        # 度量列(measure)
        for m in compiled["metrics"]:
            if m.get("entityId") == ent["id"]:
                col = {"name": m["id"], "type": TYPE_MAP.get(m.get("type","double"),"double"),
                       "is_measurable": True}
                if m.get("expression"):   # derived/ratio/cumulative → MDL expression
                    col["expression"] = m["expression"]
                cols.append(col)
        # 原始 properties
        for p in ent.get("properties", []):
            cols.append({"name": p["id"], "type": TYPE_MAP.get(p.get("type","string"),"varchar")})

        models.append({
            "name": ent["id"],
            "table_reference": {"catalog": "datafusion", "schema": ent["source"].get("schema","public"),
                                "table": ent["source"]["table"]},
            "columns": _dedupe(cols),
            "primary_key": ent.get("primaryKey"),
        })

    relationships = [_rel(r) for r in compiled.get("relationships", [])]

    return {"catalog": "wren", "schema": "public", "models": models, "relationships": relationships}

def _rel(r: dict) -> dict:
    # predicate + sourceFields + allowedJoinPaths → MDL relationship
    # 精确字段名以 wren-mdl schema 为准;此处给结构
    return {
        "name": r["id"],
        "this_model": {"name": r["from"]["entity"], "fields": r["from"]["sourceFields"]},
        "target_model": {"name": r["to"]["entity"], "fields": r["to"]["sourceFields"]},
        "join_type": r.get("joinType", "many_to_one"),
    }

def mdl_b64(compiled: dict) -> str:
    manifest = build_manifest(compiled)
    return base64.b64encode(orjson.dumps(manifest)).decode()
```

**关键设计**:这个函数是**纯函数、无副作用、幂等**——给定相同 `ontology.compiled.json` 永远产出相同 MDL。所以:
- 你的 `fingerprint.txt`(内容哈希)可复用:指纹不变 → MDL 不变 → `SessionContext` 可缓存。
- MDL 不需要落盘;但**调试期**可 `orjson.dumps(manifest)` 写到 `ontology/generated/mdl.debug.json` 供人工核对(仅 dev,gitignore)。

## 3. 模块 B · wren-core sidecar 服务(`wren_bridge.py`)

在**既有** `backend/analytics/` FastAPI 里加一个 router,不新建服务、不新增端口。复用你 `:3003`。

```python
# backend/analytics/wren_bridge.py
from fastapi import APIRouter, HTTPException
from pydantic import BaseModel
from wren_core import SessionContext          # pip install wren-core-py
from .ontology2mdl import mdl_b64
from .ontology_loader import load_compiled     # 既有:读 ontology.compiled.json + fingerprint

router = APIRouter(prefix="/api/wren", tags=["wren"])

# 指纹 → SessionContext 单槽缓存(本体指纹不变即复用,变了即重建)
_cache: dict[str, SessionContext] = {}

def _ctx() -> SessionContext:
    compiled, fingerprint = load_compiled()   # (dict, str)
    if fingerprint not in _cache:
        _cache.clear()
        _cache[fingerprint] = SessionContext(mdl_b64(compiled))   # 运行时 MDL,base64
    return _cache[fingerprint]

class SqlIn(BaseModel):
    sql: str

@router.post("/transform")
def transform(body: SqlIn):
    """SQL 经语义层(MDL)改写为 planned_sql。对应你 queryCompiler 的后处理。"""
    try:
        return {"planned_sql": _ctx().transform_sql(body.sql)}
    except Exception as e:
        # 结构化错误上抛 → Node 侧触发自愈
        raise HTTPException(status_code=400, detail=f"wren-transform: {e}")

@router.post("/dry_run")
def dry_run(body: SqlIn):
    """dry-plan 校验:不执行,只检查 SQL 在 MDL 下是否合法。= 你的 forbid_arbitrary_sql 真正落地点。"""
    try:
        return {"ok": True, "plan": _ctx().dry_run(body.sql)}
    except Exception as e:
        return {"ok": False, "error": str(e)}   # 保留错误给 agent 自愈,不抛 500

@router.get("/validate_mdl")
def validate_mdl():
    """启动/巡检健康检查:MDL 是否成功生成 + SessionContext 是否就绪。"""
    try:
        _ = _ctx()
        return {"ok": True, "fingerprint": load_compiled()[1]}
    except Exception as e:
        return {"ok": False, "error": str(e)}
```

**接入既有 app**(一行):
```python
# backend/analytics/api.py  (既有 FastAPI app)
from .wren_bridge import router as wren_router
app.include_router(wren_router)
```

**治理开关**(对应你的 constraints):在 sidecar 启动时读 `~/.wren/config.json` 或代码常量:
```python
GOVERNANCE = {"strict_mode": True,           # 所有表必须在 MDL 声明(= forbid_arbitrary_sql)
              "denied_functions": ["pg_read_file","dblink","lo_import"]}  # 危险函数黑名单
```
`strict_mode=True` 是你 5 条 constraints 里**目前唯一靠结构成立但标志没被读**的 `forbid_arbitrary_sql` 的**真正运行时落地**——这是本方案性价比最高的即时收益之一。

## 4. 模块 C · Node 主代理消费(`wrenBridgeClient.mjs`)

Node 侧**只加一个轻客户端**,接在你既有 `queryPlanner.mjs` 的 `compileSemanticQuery` 之后。带降级——wren sidecar 不可用时自动回退到你原链路,**不破坏现有行为**。

```js
// server/ontology/wrenBridgeClient.mjs
const SIDECAR = process.env.ANALYTICS_URL || "http://localhost:3003";

export async function transformViaWren(sql) {
  const r = await fetch(`${SIDECAR}/api/wren/transform`, {
    method: "POST", headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ sql }),
  });
  if (!r.ok) throw new Error(`wren-transform ${r.status}`);
  return (await r.json()).planned_sql;
}

export async function dryRunViaWren(sql) {
  const r = await fetch(`${SIDECAR}/api/wren/dry_run`, {
    method: "POST", headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ sql }),
  });
  return await r.json();   // { ok, plan? } | { ok:false, error }
}
```

**接入点**(`server/ontology/queryPlanner.mjs`,你既有 `:98-118` 编译段之后):
```js
// compileSemanticQuery(frame) 之后,增加 wren 后处理 + dry-plan 校验
let planned = await compileSemanticQuery(frame);
try {
  const rewritten = await transformViaWren(planned);          // 语义层改写
  const check = await dryRunViaWren(rewritten);               // dry-plan 校验
  if (!check.ok) {
    // 结构化错误 → 喂回 agent 自愈(复用你现有 diagnose_analytics_empty 模式)
    return { recoverable: true, hint: check.error, stage: "wren-dry-run" };
  }
  return { query: rewritten, wrenValidated: true };
} catch (e) {
  // sidecar 不可用 → 静默降级到原链路,不阻断
  return { query: planned, wrenFallback: true };
}
```

> 这段直接呼应你架构审计里的两个缺口:① 给 `queryPlanner` 补"dry-plan 校验 + 结构化错误"(WrenAI 的 correctness primitive);② 失败结果可被 agent 自愈消费(你已有空结果自愈,这里是 SQL 校验失败自愈)。

## 5. 模块 D · 借鉴(纯自研,不引 WrenAI 依赖)

这些**不嵌入 wren-core**,而是照搬 WrenAI 的设计思想,用你现有 Node/JSON 栈实现。对应你《目标架构设计.md》的 P1 项。

| WrenAI 概念 | 借鉴到你 Data-Agent 的方式 | 对应你的缺口 |
|---|---|---|
| **context layer**(`instructions.md`+`queries.yml`) | 把 `business_rules.json`(12 条)+ 历史 golden 查询做成 agent 可召回的上下文:sidecar 用 `wrenai[memory]`(LanceDB)或 Node 侧 BM25/向量 | `business_rules` 运行时零读取 |
| **strict governance**(`strict_mode`+`denied_functions`) | §3 已落 sidecar;另把 5 条 `constraints` 其余 3 条(`claim_evidence_binding`/`not_population_statistic`)做成 queryPlanner 后置校验函数 | constraints 仅 2/5 生效 |
| **golden eval runner** | 你 `golden 9+113` 扩到断言 *SQL 行结果 + 引用命中工具结果*;加 LLM-as-judge 答案分 | 评测只覆盖路由 |
| **schema-aware retrieval** | `semanticCandidate.mjs` 接 `resolver`(你 P1.5):LLM 候选 + 你的 78 zh-CN vocab 做实体链接 | 消歧未接线 |
| **cube(预聚合)** | 对高频 KPI(DDP/regression_coverage)在 sidecar 建 MDL cube,`wren cube query` 出 GROUP BY | 性能(现每次现算) |

> `wrenai[memory]` 的 LanceDB 是可选项——若你想"纯自研不引依赖",context layer 用 Node 侧 BM25(如你的 vocab 已是词表)即可起步,后续再升级向量召回。

## 6. 接口契约(sidecar 暴露给 Node)

| 方法 | 路径 | 入参 | 出参 | 用途 |
|---|---|---|---|---|
| POST | `/api/wren/transform` | `{sql}` | `{planned_sql}` / 400 `{detail}` | SQL 经 MDL 改写 |
| POST | `/api/wren/dry_run` | `{sql}` | `{ok,plan?}` / `{ok:false,error}` | dry-plan 校验(不执行) |
| GET | `/api/wren/validate_mdl` | — | `{ok,fingerprint}` / `{ok:false,error}` | 启动/巡检健康检查 |
| POST | `/api/wren/memory/recall`(可选) | `{q,k}` | `{hits[]}` | context layer 召回(需 `wrenai[memory]`) |

契约原则:**所有 wren 能力都以 HTTP 暴露给 Node,Node 不直接碰 Python/Rust**——保持你 Node 主代理的语言纯净,sidecar 是黑盒。

## 7. 分阶段落地路线

| 阶段 | 周期 | 产出 | 验收标准 | 改 Node 主代理? |
|---|---|---|---|---|
| **P0 试水·验证 MDL 生成** | 1–2 周 | `ontology2mdl.py` + `/api/wren/validate_mdl` + `/transform`;在 2–3 个实体(`defect`/`testing_coverage`)上手工核对 | `planned_sql` 在你库上执行结果 = 原 SQL 结果**逐行一致** | ✗ 纯旁路验证 |
| **P1 嵌入主链路** | 2–3 周 | `wrenBridgeClient.mjs` + `queryPlanner` 接入(transform+dry_run+降级);`strict_mode` 接 `forbid_arbitrary_sql`;校验失败→自愈 | 灰度上线,`wrenFallback` 比例 < 5%;`dry_run` 拦截率可观测 | ✓(带降级) |
| **P2 借鉴升级** | 3–4 周 | context layer(`business_rules`/queries 召回)接 `resolver`;golden eval 扩 *答案/SQL 行/引用*;高频 KPI 建 MDL cube 预聚合 | business_rules 命中率;golden 答案准确率;KPI 查询延迟下降 | ✓ |

> **P0 是决策门**:只有 P0 证明"你的 JSON 本体能无损映射成 MDL 且 transform_sql 结果一致",才进 P1。否则退回"纯借鉴重写"路线(不引 wren-core,只抄设计)。这把不确定性锁在最小投入内。

## 8. 风险与回退

| 风险 | 影响 | 缓解 |
|---|---|---|
| **Linux ARM64 无预编译 wheel** | 部署机若是 ARM64 Linux 会装不上 | Docker 多阶段(x86_64 build)/ 固定 x86_64 部署 / 自带 Rust 工具链编译 |
| **MDL 表达不了你的某些结构**(derived/ratio metric、predicate 化关系) | 部分 metric/关系进不了 MDL | 表达不了的**留在 sidecar 自研校验层**(不进 MDL);落地前抓 `core/wren-mdl` schema 核对精确字段 |
| **SessionContext 创建开销** | 首查询慢 | §3 指纹缓存(本体不变即复用)+ 启动预热 |
| **三栈 Node/Python/Rust** | 团队认知成本 | 你**只写 Python**;Rust 是 wren-core 黑盒,不碰源码 |
| **WrenAI 上游 breaking change** | transform 行为漂移 | pin `wren-core-py` 版本;CI 跑 MDL 黄金快照对比 |
| **降级掩盖问题** | wren 不可用时静默回退,你不知道 | `wrenFallback`/`dry_run error` 全部打 telemetry + 告警(对应你 P0.1 可观测) |

**总回退**:`wrenBridgeClient` 任何异常都 `catch` 并回退到 `compileSemanticQuery` 原链路——**wren sidecar 挂掉 = 退回你今天的行为**,不会让系统不可用。这是本方案的安全网。

## 9. 明确边界:这些**不要**碰(避免过度集成)

- ✗ `wren` CLI / `wren_project.yml` / MDL YAML 项目——违背"JSON 为唯一源",会引入双本体漂移
- ✗ `wren serve mcp` 整体接入——那是"整体上 WrenAI"路线,会让 WrenAI 取代你的 agent 编排
- ✗ `wren genbi` / `wren-core-wasm` dashboard——离"问数 agent"需求远,投入产出比差
- ✗ 放弃你的 `ontology/v1` JSON 治理(校验器/指纹/脱敏)——这是你**比 WrenAI 更强**的地方,别丢
- ✗ 把 `business_rules`/`constraints` 全塞进 MDL——它们在 sidecar 自研校验层(§5)更灵活,MDL 只管"表/列/关系/度量"

---

## 10. 总结:这条路线的本质

**把 WrenAI 当"语义引擎 sidecar 库",不当"框架"。** 你的 JSON 本体、agent 编排、治理体系全部保留;wren-core 只负责"SQL 经语义层改写 + dry-plan 校验"这一个能力——而这正是你架构审计里最弱、性价比最高的一块。

- **即时收益**(P1 即可得):`strict_mode` 让 `forbid_arbitrary_sql` 首次真正生效;`dry_run` 给你 `queryPlanner` 缺失的"宁可失败也不幻觉"校验层;`transform_sql` + MDL relationships 让你 27 条**零调用**的关系首次有运行时图遍历落地。
- **它不解决一切**:`business_rules` 消歧接线、多 agent、失败 run 审计仍要按调研报告的 P0/P1/P2 自研——wren-core 只把"语义层引擎"这一块补到工业级。
