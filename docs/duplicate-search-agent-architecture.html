Duplicate Search Agent 设计架构与业务流程

这个 agent 不是一个孤立的聊天机器人，而是一条由前端交互、Node 网关、Python 检索桥、SQLite 数据源、反馈式 rerank 共同组成的本地检索链路。 它的目标很明确：把“当前问题”快速映射到“历史最可能重复的 defect”，再生成简洁可执行的判断摘要。

核心定位 独立重复缺陷检索能力，也可作为 AI Chat 的上下文召回层。
主要接口 /api/duplicate-search、/api/duplicate-feedback、后台 warmup。
检索策略 Hint 抽取 + 向量或 TF-IDF 粗召回 + 渐进式 rerank + LLM 或 fallback 总结。

1. 架构总览

从实现上看，这条链路分为四层，每层职责边界比较清晰。

Layer 1

UI 入口层

  • AI Chat 页面里有一个独立的 Duplicate Search 模式切换。
  • 用户输入现象、项目、PU、日志关键词后，前端向本地 API 发请求。
  • 页面会先展示“正在检索”状态，再渲染摘要与候选 ticket 列表。
Layer 2

Node 网关编排层

  • 统一暴露 /api/duplicate-search 与 /api/duplicate-feedback。
  • 通过常驻 JSON Line bridge 复用 Python 子进程，避免每次请求都重启检索内核。
  • 在拿到候选后，再调用 summary 逻辑生成用户可读结论。
Layer 3

Python 检索桥层

  • 负责数据加载、DataFrame 缓存、索引缓存、hint 抽取、检索与反馈落库。
  • 支持三种 action：search、warmup、feedback。
  • 把复杂检索逻辑隔离在 Python 侧，Node 只负责编排。
Layer 4

数据与学习层

  • 主数据来自 SQLite octane_defects 或本地 defect JSON。
  • Embedding、feedback、模型快照保存在本地 SQLite。
  • 检索结果会受到历史 click/positive/negative 反馈影响。

2. 关键模块拆解

前端交互

  • src/components/dashboard/pages/AIChat.tsx 同时承载聊天与 duplicate search 模式。
  • Duplicate Search 模式不支持附件，强调文本现象检索。
  • 独立模式返回候选列表和摘要；普通 AI Chat 模式则可把 duplicate search 结果当作上下文。

运行时桥接

  • server/duplicateBridgeRuntime.cjs 维护一个常驻 Python 进程。
  • 通信协议很轻：Node 写入一行 JSON，请求；Python 回一行 JSON，响应。
  • 好处是简单、跨平台、易排障，也方便在本地环境复用现有 Python 检索代码。

检索桥

  • scripts/duplicate_search_bridge.py 会优先解析 SQLite，退化时再读取 defect JSON。
  • Bridge 内维护 defect DataFrame 缓存和 index cache key，减少重复构建。
  • 对外统一输出 searchId、candidates、timings、modelPhase 等字段。

检索核心

  • backend/duplicate_issue_finder.py 会先从 query 中提取 project、PU、ECU、lead model 等 hint。
  • 优先使用本地 sentence-transformer embedding，失败时回退到 TF-IDF，再不行则走 keyword fallback。
  • 对匹配到的 project/PU/ECU 做 boost，并过滤掉默认不参与检索的 phase 前缀。

反馈学习

  • backend/feedback_store.py 记录 click、positive、negative 信号。
  • 它还负责 rate limit、同用户短时间反向反馈覆盖、训练阶段判定。
  • 反馈量越多，rerank 从简单 click boost 逐步升级到 feature / adapter phase。

结果总结

  • server/duplicateSummary.mjs 会把 Top-N 候选转成简明 prompt。
  • 如果配置了聊天模型凭据，就用 LLM 输出 6 行内中文结论。
  • 如果没有可用模型，则退回到 deterministic fallback summary。

3. 业务流程

你项目里实际上有两条业务链路，共享同一个 duplicate search 内核。

流程 A: 用户主动做重复缺陷检索

前端切到 Duplicate Search 模式，用户输入“现象 + 项目 + PU + 日志关键字”。
Node 接收 /api/duplicate-search，把 action=search 发送给 Python bridge。
Python 加载 defect 数据，构建或复用索引，抽取 hints，然后执行 coarse search + rerank。
Node 对结果做摘要，再把候选 ticket、评分、摘要一起返回给前端展示。

流程 B: AI Chat 把它当作上下文召回层

用户仍在 AI Chat 中提问，但开启了“缺陷上下文”。
server/aiContext.mjs 提取最后一条用户消息，先调用 duplicate bridge 检索相关 defect。
系统把 Top 结果格式化成一段结构化 defect context，注入后续 AI 对话请求。
最终大模型回答不只是“聊天”，而是带着 qgate 历史缺陷上下文的回答。
关键业务价值：duplicate search 既能独立给出“可能重复票”，也能作为 AI 的召回底座，减少大模型在缺陷排查上的盲答。

4. 检索过程内部机制

Query 解析

从自然语言里抽取 project、PU、ECU、lead model，形成 hint。

粗召回

优先 embedding，相同文本走 embedding cache；无模型时退化到 TF-IDF 或关键词匹配。

重排序

基于 feedback 做 click boost 或 feature re-rank，让历史有效候选更容易上浮。

摘要输出

返回结构化候选结果，再由 Node 侧进行人类可读总结。

为什么要 warmup

  • 首次请求最慢，主要耗时在数据加载与索引构建。
  • server/duplicateWarmup.mjs 在服务启动时触发后台 warmup。
  • 这样用户第一次搜时更像“热命中”，减少冷启动感知。

为什么要独立 Python bridge

  • 现有检索与数据处理代码主要是 Python 资产，直接复用成本最低。
  • Node 负责对前端友好的接口、SSE、AI 编排，Python 负责算法与数据。
  • 这比把检索逻辑完全重写到 JS 更稳，也更便于后续调试与实验。

为什么要 feedback

  • 重复缺陷判断很依赖领域经验，纯相似度排序不够稳定。
  • 反馈把“实际好结果”变成可学习信号，逐步修正排序。
  • 所以它不是纯静态搜索，而是一个可渐进优化的检索 agent。

6. 一句话总结

从工程角度

Duplicate Search Agent 是一个由 React 页面触发、由 Node 编排、由 Python 执行检索、由 SQLite 承载状态、并能借助反馈持续改进排序的本地检索系统。

从业务角度

它解决的是“当前问题像不像历史某个 defect”这个高频场景，并把答案包装成可读、可操作、可继续学习的结果，而不是只返回一堆相似文本。

文档基于当前仓库实现整理，适合演示、交接与新成员快速理解 duplicate search agent。
