# Duplicate Search Agent 技术分享 PPT 设计

日期：2026-07-14
状态：等待最终规格确认

## 1. 沟通任务

在 30 分钟正文和 10 分钟问答结束时，测试、产品、技术和管理层应形成对 Duplicate Search Agent 的共同认知，理解它解决什么业务问题、如何完成判断、为什么当前方案可信且不过度设计，以及为什么下一阶段应优先投入评测与可验证的模型升级。

主结论：Duplicate Search Agent 不是一个“大模型黑盒”，而是一条由语料治理、混合召回、结构化约束、渐进式重排、证据解释和用户反馈组成的业务闭环。

## 2. 受众与内容深度

- 测试：能理解如何使用结果、如何复核候选、反馈如何产生价值。
- 产品：能理解体验链、信任机制、业务边界和冷启动限制。
- 技术：能理解 Embedding、字符级 TF-IDF、RRF、Hints、Rerank、缓存和降级的技术原理及取舍。
- 管理层：能理解业务价值、当前完成度、主要风险和下一步资源投入顺序。

可见内容不进入代码级模块名和函数名。允许展示真实技术名词、模型名、阶段阈值和约 1.6 万条活跃缺陷的数据规模，但不展示真实缺陷内容、VIN、内部日志、人员信息或访问凭据。

## 3. 叙事结构

采用“问题 → 机制 → 闭环 → 取舍 → 行动”的累计式叙事，并用一个匿名蓝牙连接失败案例贯穿输入、召回、过滤、输出和反馈。

### 第一章：先把问题讲明白，约 5 分钟

1. **把相似问题找出来，也把依据讲清楚**
   最简标题页；只给出分享承诺。
2. **重复缺陷不是“文本长得像”**
   用两个匿名缺陷对比说明“同义不同词”和“同词不同事”。
3. **一个蓝牙连接失败，人工要翻多少历史记录？**
   匿名案例登场，展示现象、DTC、版本和 ECU 等线索，以及人工查找的摩擦。

### 第二章：系统如何做判断，约 13 分钟

4. **一次查重经过五个环节**
   业务泳道图：语料整理、两路召回、融合、重排、解释与反馈。
5. **Embedding 把“说法”映射成“位置”**
   用语义空间图解释向量表示；说明选择 BGE-small-zh-v1.5 是中文效果、512 维轻量化、本地部署与数据安全之间的平衡。
6. **字符检索负责守住编号与日志**
   用字符切片图解释 char n-gram TF-IDF，突出 DTC、版本号、错误码等硬实体。
7. **RRF 融合的是名次，不是硬凑分数**
   用两条排名梯子展示 Dense 与 Sparse 的分数尺度不同，以及 Reciprocal Rank Fusion 的稳定性。
8. **结构化条件让“像”更接近“真重复”**
   匿名案例回归；Project 和 PU 作为硬约束，ECU 和 Lead Model 作为软加权。
9. **好检索先从干净语料开始**
   用评论“保留 / 过滤”对比图说明系统流水与分析证据的区别。
10. **索引与缓存让模型不必每次重来**
    用数据流图展示增量编码、Embedding 缓存、索引快照、预热和降级路径。

### 第三章：为什么它称得上 Agent，约 6 分钟

11. **它不是一个模型，而是一条协作链路**
    四层技术架构图：交互层、服务编排层、检索与学习层、数据与缓存层。
12. **反馈让排序逐步贴近真实业务**
    阶梯图展示 Click Boost、Feature ReRanker 和 Contrastive Adapter；同时展示速率限制与 nDCG 安全护栏。
13. **LLM 负责解释，不替检索拍脑袋**
    真实项目 UI 截图式页面，标注置信度、Evidence、Ranking Signals、Octane 跳转和反馈入口；强调候选先由检索与重排确定，LLM 只生成短结论与复核重点。

### 第四章：工程取舍与边界，约 3 分钟

14. **1.6 万条数据，不需要先上重型向量库**
    用规模与复杂度对比图解释当前使用 NumPy 矩阵检索、SQLite 缓存和轻量进程桥的合理性；规模超过约 10 万后再评估 ANN 或专用向量数据库。
15. **当前最缺的不是更大的模型，而是评测基线**
    诚实说明冷启动、查询规范化、人工标注集和 Recall@k / nDCG / MRR 基线的缺口。

### 第五章：下一步，约 3 分钟

16. **先用数据证明提升，再投入模型升级**
    行动路线图：先建 100–300 对标注集和基线，再验证查询规范化、Cross-Encoder、稀疏召回升级和 Embedding 升级。明确四类角色的投入：测试给标注、产品定口径、技术建评测与实验、管理层提供试点时间和算力资源。

## 4. 视觉设计

视觉方向采用已确认的“工程手记”：

- 16:9 宽屏。
- 暖灰纸张色为主背景，炭黑为正文，青绿表示检索链路，橙色表示关键判断和匿名案例。
- 不使用渐变、发光、玻璃效果、满屏卡片、装饰性 AI 插画或口号式标题。
- 标题像真实分享者会说的话，优先给结论，不使用机械式“从 X 到 Y”。
- 版式保持平面化，以一张主视觉承载一页结论，文字只做解释。
- 正文至少 16pt，页标题至少 35pt，封面标题至少 50pt。
- 采用无衬线中文字体，优先使用系统可用的思源黑体 / Noto Sans CJK；若不可用则使用苹方或微软雅黑兼容字体。

## 5. UI/UX 呈现

UI/UX 不以整页截图堆叠，而是组合三种表达：

1. 四状态体验链：输入、检索中、结果判断、行动与反馈。
2. 真实候选结果局部截图：置信度、相似度、Evidence、Dense / Sparse 排名、反馈控件。
3. 业务泳道：测试工程师、Vizion、查重引擎、Octane / 数据四条泳道，说明结果如何进入真实复核流程。

截图使用匿名蓝牙案例和虚构票号，不复制真实生产缺陷正文。

## 6. 准确性与边界规则

- 明确区分当前实现与未来路线图，不把建议能力描述成已上线能力。
- “置信度”是确定性校准分，不描述为统计概率。
- BGE-small-zh-v1.5、字符级 TF-IDF、加权 RRF、Hints、渐进式重排、反馈阈值和缓存机制以当前仓库实现为准。
- LLM 仅用于结果摘要和复核重点，不将其描述为候选检索或最终排序的唯一决策者。
- 不宣称当前方案已经达到 SOTA；说明系统已有完整工程骨架，但系统化标注集和可复现评测基线仍需补齐。
- 不承诺未经测量的准确率、延迟改善或业务节省量。
- “约 1.6 万条”沿用现有项目资料的规模口径，页面明确标注为近似值，不把它呈现为实时统计。
