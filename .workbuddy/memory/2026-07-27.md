## Agent 架构现状澄清 + LangGraph/Pi 选型（用户问询）

- 用户记忆/云档案中"当前仍是单轮 RAG + 表现型 agent、缺 agent 循环"的描述**已过时**。实际 `server/agentRuntime/` 已是成熟运行时：graph.mjs（图编排，runtimeMode="langgraph" 自研同名引擎）、contracts（schema 校验）、policy（准入/限流）、checkpoint（续跑/回放）、threadStore（长期记忆）、audit+shadow（可观测/HITL）、modelRegistry（deepseek-v4/qwen3.5/glm-5/glm-5.2 多模型）。流水线为 intent→ontology→plan→claims→tool 循环。
- 判定：当前架构**已是混合（hybrid）agent 架构**——确定性控制面包裹随机 LLM 专长角色（对标 2026 Spacebot"克制式"/Qualcomm 云边协作范式）。
- 选型结论（用户问"直接用 LangGraph 或 Pi 如何"）：(1) 保持自研引擎，勿推倒重来；LangGraph 仅在其平台红利（LangSmith/Studio 可视化调试、全链路追踪）成为痛点时引入，不必换运行时。(2) Pi agent 家族整体对编排是降级（无图/无 checkpoint），仅 `pi-ai` 统一多模型流式层值得借来替换 `modelAdapter.mjs` 做干净的多 provider + 自动降级；若用户本意是 Pydantic AI，则只能作为引擎之上的工具调用封装，不替代运行时。(3) 最高性价比下一步：利用 modelRegistry 已有的"按节点路由不同模型"能力，做 SLM（glm-4.7/qwen 小尺寸）做 intent/claims 初筛 + 前沿模型（glm-5.2/deepseek-v4）做 plan/tool 规划的 SLM+LLM 分层。
